# ADR 0027: Platform-admin subscriber directory

Status: accepted for the owner-selected read-only directory slice on 2026-10-22; independently verified and deployed only to development. [Final review](../reviews/admin-subscribers-2026-10-22/independent-validation.md), [deployment/preservation](../reviews/admin-subscribers-2026-10-22/deployment.md). Owner acceptance, ADM-07, subscription mutations and other admin modules remain open. Milestone 5 stays open.

Related requirement IDs: ADM-01
Supersedes: none. The examination text in [the 2026-10-22 plan](../operations/admin-subscribers-plan-2026-10-22.md) remains historical.

## Context

The React administration client could authenticate a platform administrator and persist the theme, then showed a prototype shell. Shop owners already see subscription status through `list_my_shop_accounts`: pending when no entitlement exists or the server clock is before `starts_at`, active when `starts_at <= now() < expires_at`, and expired otherwise. `now()` is the transaction timestamp. Platform administrators are not shop members and must not receive shop financial, customer, invoice, media or contact data.

## Options considered

| Option | Benefits | Costs and risks |
| --- | --- | --- |
| A. Grant platform administrators `SELECT` on `shops` and `shop_entitlements` | Small client query | Exposes phone, email, location and owner name. Weakens the owner-only table boundary. |
| B. Narrow security-definer read functions that return an allowlisted snapshot | Live admin and session checks on every call. One statement owns the rows and the counts. Contact columns stay unselected. | Requires a dedicated contract and tests. A later column added to the JSON would have to be reviewed. |
| C. Reuse `is_platform_admin()` as a client-side flag and read through existing shop RPCs | Reuses a function that already exists | Those RPCs are owner-scoped. A client flag is not authorization. User metadata is not authority. |

## Decision

Option B. `public.admin_list_subscribers_v1` and `public.admin_get_subscriber_v1` are the only new client entry points. Both are stable security-definer functions with `search_path` empty. Each request calls `private.admin_subscriber_gate()` inside the same SQL statement as the shop read. The gate returns `unauthenticated` when `auth.uid()` is null and `session_expired` when `private.caller_session_accepted()` is false. It then rejects an identity whose `banned_until` is still in the future. Identity and `platform_admins` membership otherwise come from `public.is_platform_admin()`. Metadata is not read. A currently banned administrator fails even when that function would return true. Anonymous callers, ordinary owners, count-only staff, revoked administrators, deleted identities, currently banned administrators and expired or unknown sessions fail. A missing session claim remains acceptable, matching the existing session helper used by SQL fixtures.

The page returns `snapshot_at`, global `all` / `active` / `pending` / `expired` counts, a separate `filtered_count`, `page_size`, rows and `next_cursor`. Counts are decimal strings. A row contains shop id, shop name, registration time, entitlement start, entitlement expiry and the server status. Shops with no entitlement are included and are pending. A future term is pending. An expiry equal to the server clock is expired. The detail function returns the same shop fields plus `snapshot_at`.

Search is a trimmed literal substring, at most 120 characters, with control characters rejected. `%` and `_` are not pattern wildcards. A complete UUID is parsed once with `CASE` and then compared with the shop id. The cast does not depend on `AND` evaluation order. A partial UUID does not match. Status filters are `all`, `pending`, `active` and `expired`. Page size is 1 through 25. The client asks for 20. Order is `created_at` ascending, then `id` ascending. The cursor is exactly three canonical fields, `v1`, a UTC timestamp `YYYY-MM-DD HH24:MI:SS.US`, and a UUID, 66 characters, with no empty extra separator. It is stale when that shop is missing or its registration time differs. Each response's rows and counts come from one statement, so that response has one transaction snapshot. The cursor is a keyset position. It does not freeze later pages. A shop registered after the response can appear on a later page when its key is after the cursor, and a refreshed first page can show it too. An earlier draft of this ADR said an issued cursor could not show a later registration. That was stronger than the SQL. This record does not add a cursor snapshot.

`EXECUTE` is granted only to `authenticated` on the two public functions. The gate and payload helpers are not granted. `service_role` is revoked when that role exists. No table grant, policy or financial function changes. The index `shops_registration_order_idx` on `(created_at, id)` supports the keyset order.

The React page is Arabic and right-to-left. It shows the four global counts apart from the filtered count, and one data-as-of time in the browser display zone with an Arabic zone name. Dates use Latin digits. Shop names are headings. Subscription fields are a definition list. Large counts may wrap. A desktop table starts at the `md` breakpoint, and cards are used below it. The directory measure is 1120 pixels so the six fields remain readable. Shop surfaces stay at 720. Status text comes from the server and is not derived from the device clock. A pending row with a start time says the term has not started. A row with both dates empty says there is no subscription term. Loading, empty, retry, refresh and access-loss states are explicit. Losing admin access clears the page and asks the auth gateway to refresh. A changed filter clears the previous page before the next response. Late responses from an older request are ignored. A directory read captures the session before the call and checks it again afterward. Sign-out, a different account, or a replaced session drops the reply. A same-user token refresh retries once or fails as retryable, and the applied search and filter stay in place. Explicit sign-out or an account change clears admin state immediately and invalidates an in-flight admin check. Valid search and filter state survive refresh and a visible-tab revalidation. Subscription status is labelled as independent of owner-account access. Unimplemented admin actions are not shown.

## Data and compatibility impact

Migration [20261022094412_admin_subscriber_directory.sql](../../supabase/migrations/20261022094412_admin_subscriber_directory.sql) adds the index/functions without rewriting shops, entitlements, finance, dispatch or audits. The earlier local 20261022082352 filename was aligned with the actual hosted identity without changing its contents. Existing owner-scoped APIs still deny implicit admin access. Transaction rollback/reapply was verified locally; old clients ignore the additive read RPCs. The response parser rejects extra keys, numeric counts and inconsistent totals.

## Verification

Local and rollback-only hosted fixtures verify role/session boundaries, exact term boundaries, missing/future terms, literal/UUID search, keyset paging, global/filtered counts and preserved data. Paging inserts are tested on one connection; no frozen cross-page snapshot or two-connection concurrency is claimed. React tests cover session replacement, refresh/retry, exact values and critical UI paths. [Independent review](../reviews/admin-subscribers-2026-10-22/independent-validation.md) includes 43 Arabic browser captures, keyboard scrolling/focus and pending/failed sign-out. [Development evidence](../reviews/admin-subscribers-2026-10-22/deployment.md) records hosted source identity and preservation; owner acceptance remains separate.
