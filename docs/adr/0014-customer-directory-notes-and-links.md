# Customer directory, notes and explicit transaction associations

Status: CRM-01/CRM-03 implemented and verified in development. Native owner/device acceptance remains open. Date: 2026-10-13.

The submitted [slice prompt](../operations/customers-slice-prompt-2026-10-13.md) bounds the PAGES customer requirements to directory/phones, notes/latest preview, VIP/open-request status and explicit confirmed-operation associations. The source customer mockup supplies card/header/dated-note structure. Its weight statistics, calls, WhatsApp, contact-saved state, request reminders and sharing controls are excluded. [Owner access](0003-owner-only-shop-access.md), [immutable finance](0009-milestone-3-accounting-working-rules.md), repairs and [debt contracts](0013-debt-balances-and-settlement.md) remain intact.

## Working rules and source differences

A customer has a required Arabic display name; mixed names containing Arabic are accepted. Names are trimmed, limited to 200 Unicode characters and reject controls. The submitted prompt requires an Arabic display name; PAGES does not prescribe a script validator. These are bounded implementation rules, not a complete international naming policy.

PAGES lists phones but does not state that one is mandatory. Customers may have none, or up to ten numbers with exactly one primary. Normalize Arabic/Persian digits and separators, Egyptian domestic/mobile/landline formats, international + and 00 prefixes. International validation is structural E.164-style validation, not proof of ownership, connectivity or WhatsApp state. Numbers from another country require a dial code. Duplicate normalized numbers within a record and conflicting ownership within a shop are rejected. The same number may belong to a different shop. Archived records retain their number reservations until explicitly edited.

The submitted prompt narrows PAGES edit/delete wording: notes are immutable dated entries, and deletion is reviewed archive/restore. New notes do not replace old ones. Multiline notes are supported, trimmed and limited to 1000 Unicode characters; other control characters are rejected. VIP and open request are audited booleans, not a request/reminder subsystem. The owner may edit contact metadata, append notes and change those flags on archived files; adding a transaction association requires an active file. Archived files retain existing links and allow audited unlink correction. Restore returns the file to the normal directory.

No matching name or phone imports or merges transaction, repair or debt parties. A reviewed association identifies one existing sale/purchase by immutable operation ID, sequence, kind, party snapshot and server time. The operation must belong to the shop and have its confirmed detail/audit evidence. One active customer association is allowed per operation. Unlink followed by an explicit new link corrects the association; the old row and both audit entries survive. Financial payloads, invoice snapshots, cash, stock, gold, custody, debt and business-day versions are untouched.

## Authority, recovery and display

Six CRM tables use owner/session RLS and prohibit direct client writes. Twelve authenticated RPCs reuse the existing reader/entitlement contract and narrowly granted private helpers. Platform administrators gain no shop access. New writes lock the shop then customer, check the expected record version, and atomically write state, immutable audit, request result and sync. Same key plus exact payload replays the original result; another payload is rejected. Expired owners may read/reconcile completed requests; revoked or expired sessions cannot read. No Auth policy changed.

The shared durable command locker freezes one owner/shop request across restart and uncertainty. Customer status checks include key, kind, customer ID and exact original payload. Malformed or mismatched receipts remain pending; failed local cleanup preserves the blocking request. The ledger routes customer recovery to Customers rather than opening/financial status. Duplicate submissions are disabled. Caller/token changes discard replies, and access loss clears displayed customer data.

Search and name/actual-linked-operation sorting use bounded 20-row client pages, server limit 50, and cursors bound to query/sort/filter or customer/detail channel. Invalid cursors are explicit errors. Customer updates and association timestamps are distinct from actual transaction time. Customers without linked activity have an honest empty state. Server UTC is authoritative; server-derived shop wall time is displayed with LTR isolation. Shops currently have a time-zone setting and the app has fixed Arabic locale, so CRM returns locale ar without inventing a separate shop-locale setting.

Customer revisions extend the existing protected shop-sync signal. Reconnect refetches authoritative records; an invalidation during edit/review preserves the draft and blocks stale confirmation until reopened. Shared brown/cream/dark roles, Cairo, RTL and 720-pixel content measure remain unchanged.
