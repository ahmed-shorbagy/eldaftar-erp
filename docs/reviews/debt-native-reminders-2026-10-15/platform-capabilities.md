Implementation began 2026-10-15; final checks continued 2026-10-16, Africa/Cairo. [Confirmed D19/D33](../../adr/0020-native-debt-reminders.md). Android, iOS and Windows are included; none was owner-deferred. Compilation, synthetic adapters, OS registration and actual delivery are separate evidence levels. No real OS notification was scheduled by this task.

Shared dependency: exact flutter_local_notifications 22.3.2 and timezone 0.11.0; Flutter 3.38.5 / Dart 3.10.4; app 1.0.0+1. Revisit the pinned native/cache contracts before upgrading.

All platforms use generic Arabic title/body and an opaque random route token, with no party, phone, amount, unit, karat, credential or authenticated URL. Scheduler queue items contain exactly five identity/freshness/time/validity fields. A bounded encrypted 64-route history preserves authenticated taps after firing; account changes discard routes. Taps freshly reread authorized source data. Neither permission nor registration proves display/read/delivery, payment or dispatch.

The owner accepted duplicate notifications across enabled installations and stale generic requests when a closed/offline device cannot learn settlement/archive/revocation. Expired authorized readers keep confirmed intent and local disable; shared writes remain active-entitlement-only. Logout/access loss cancels when the app can act. No remote provider/device-token registry is introduced.

Android boot integration deliberately depends on the exact 22.3.2 scheduled_notifications cache and package-visible reschedule method. It filters only the owned ID/channel/token/UTC/one-shot shape, retaining foreign JSON objects/unknown fields. Pure JVM policy tests do not establish receiver/reboot/device delivery; compile checks and static native review are recorded separately.

Primary references checked: [Android alarms](https://developer.android.com/develop/background-work/services/alarms), [Android permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission), [Apple local notifications](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app), [Apple authorization](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications), [Windows scheduling/cancellation](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-scheduled), [pinned plugin documentation](https://pub.dev/packages/flutter_local_notifications/versions/22.3.2). Installed pinned Android/iOS/Windows source verified API shapes, pending/cancel behavior and lifecycle setup. Apple reference content is script-rendered; inspected native source is call-shape evidence, not device proof.

Remaining acceptance requires separately authorized controlled synthetic notification QA on Android/iOS/Windows: Arabic OS content, permission recovery, sound/Focus/DND, process death, reboot/force-stop, clock changes, repeated registration/cancellation and authenticated cold/warm taps. One platform's adapter tests never substitute for another or physical hardware. DEBT-03 remains open for these acceptance gaps.
