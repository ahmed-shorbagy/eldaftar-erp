# Daily ledger financial workflow review — 2026-09-28

## Local implementation

- Sale, purchase, and expense forms compose exact integer piastres, milligrams, and counts. They review the net cash and gold effect before sending one idempotent command.
- The purchase form now separates total price from cash paid. For shop-owned partial or zero-cash purchases, it requires a named seller, reviews the EGP payable, adds the full owned gold only once, and exposes an exact cash settlement that reduces the payable without another gold movement. This is a bounded cash-payable path under [ADR 0007](../../adr/0007-purchase-ownership-and-custody.md), not the financier custody or gold-debt path.
- Manual close compares entered cash, stock, and scrap counts with the server snapshot, blocks a discrepancy, and seals the day only after server confirmation. Explicit next-day opening has a separate command.
- Confirmed operations can open an owner-scoped detail view with server actor, time, sequence, items, tenders, customer, and note where present.
- The confirmed dashboard reads daily sale, purchase, and expense totals and operation counts from the version-two server read model, separate from the current cash balance. It also lists confirmed sale and purchase gold weight and piece count by category and karat, with exact cross-category totals for a selected karat. The owner can show, hide and reorder the daily movement, cash, gold and activity sections, and each sale/purchase/expense/gold movement card within daily movement. Arabic RTL gold movement and saved-card-order widget checks passed at 320 and 1440 logical pixels in light and dark themes; a live device rendering remains unverified.
- The activity feed now carries a server-derived note marker and recognizes purchase-settlement events; the previous client parser would reject a confirmed feed after settlement. The regression fixture includes that event and note flag.
- One pending command per owner and shop is saved in platform-protected storage before sending. A restart checks the same idempotency key and retries the original body. Existing valid plaintext SharedPreferences retries are moved to protected storage and removed from the old entry. Other financial controls stay unavailable while that outcome is unresolved.
- An active confirmed ledger refreshes from the server each minute and on app resume. The pre-migration opening read model remains available if the version-two RPC is missing; financial controls stay hidden until the day-state RPC exists.
- The shared Flutter theme now uses the bundled Noto Sans Arabic font. Colors continue to derive from the existing brown/cream `ColorScheme`.
- A confirmed sale or purchase can generate an Arabic A4 PDF customer copy from the server operation payload and open a WhatsApp text draft or PDF share action. An open handoff remains unconfirmed. A separate owner confirmation RPC records its actor and UTC time; the operation screen reads the confirmed state on other sessions. The manual-send policy is in [ADR 0006](../../adr/0006-owner-confirmed-whatsapp-dispatch.md).
- The owner can open a paginated pending-send queue from the ledger. Confirmed sale and purchase documents appear until owner confirmation, including across older business days.
- Cash transfer between existing payment methods has a reviewed exact amount, from/to balances and unchanged cash/gold total. Its owner-only server command writes one balanced journal, audit event, operation detail and outbox event under the same idempotency key. A rejected overdraft leaves no operation. The active ledger refreshes after confirmation.
- The scrap-to-cash quick action is a distinct confirmed «بيع كسر» operation. It requires shop-owned scrap in an allowed karat, reduces exact milligrams, increases one or more payment-method balances, and includes the cash in the daily sales summary. The form reviews the loss of scrap and cash gain before sending; the server rejects a stock item or scrap overdraft and replays the original command without duplicate gold or money movement.
- Same-karat scrap-to-stock is a separate owner command. It subtracts exact milligrams from the selected scrap bucket, adds the same milligrams and an explicit piece count to an allowed saleable category, leaves every cash method unchanged, and records its actor, server time, detail, audit and outbox atomically. Its connected-project migration and rollback SQL gate passed on 2026-09-30, including overdraft rejection and idempotent replay.
- A full linked sale/purchase return is deployed. It preserves the original operation, creates a new operation in the current open day, reverses the original balanced journals, also reverses every linked purchase cash settlement, and cancels the remaining purchase payable. The operation screen prevents a second return after the server reports the link. The product owner explicitly approved the live balance-changing migration on 2026-09-30.

## Acceptance limits

The trade, dispatch, cash-settlement, cash-transfer and scrap-sale migrations were applied to the sole connected Supabase project on 2026-09-29, followed by scrap-to-stock and linked returns on 2026-09-30. The rollback-only `supabase/tests/daily_ledger_trades.sql` passed after every migration. It covers arithmetic, idempotency, owner isolation, close/reopen, note markers, dispatch state, partial cash settlement, cash transfer, scrap sale, scrap-to-stock, full sale return, full purchase return after settlement, payable cancellation, duplicate-return rejection and overdraft rejection. Project counts before and after the final rollback remained one shop, one opening operation, zero journals, one business day and one command request. No real two-session race, device run, or customer flow has been verified.

Local checks on 2026-09-30: Dart format completed and the full Flutter suite passed with 213 tests, including linked-return and scrap-to-stock HTTP, protected-retry, effect-review, Arabic RTL, 320/1440 width and light/dark regressions. Both full and scoped Flutter analyzer commands produced no diagnostics but did not terminate after two minutes and were stopped; successful compilation of all 213 tests is recorded separately from that incomplete analyzer gate. React lint, 34 tests and `npx tsc -b` passed. The rollback-only SQL gate passed on the connected project after the scrap-to-stock migration. Windows and Android debug builds passed with the protected-storage plugin before the later quick actions were added; no release builds were run.

The retry envelope now uses `flutter_secure_storage` (11.2.0) with a one-time plaintext migration. Android auto backup is disabled so encrypted values cannot be restored without their device key. Unit/widget recovery and Android/Windows debug compilation passed; an actual restart and keychain failure exercise on Android, iOS and Windows devices remains open. No real customer data was used in local fixtures.

The connected-project security advisor reports the authenticated `SECURITY DEFINER` financial RPCs, now including scrap-to-stock and linked return, alongside the existing owner commands. That exposure is intentional: each command resolves the signed-in owner's shop on the server, checks the active entitlement and current open day, and the rollback SQL gate checks cross-shop reads and unauthorized financial paths. The advisor also reports leaked-password protection disabled in Supabase Auth and pre-existing RLS-without-policy information notices for deliberately inaccessible audit/reservation/admin tables. [Function advisory](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable), [password protection guidance](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

The original source requirements extend beyond the bounded rules approved in ADR 0005: financier/trader custody, gold-denominated obligations, partial returns and exchanges, inventory lots, notes with images, template customization, image export, and reports remain open in the requirements matrix. The approved ownership/custody rule in [ADR 0007](../../adr/0007-purchase-ownership-and-custody.md) is only partially implemented by the shop-owned EGP payable path.
