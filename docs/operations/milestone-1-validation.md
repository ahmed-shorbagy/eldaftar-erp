### Migration design recorded before application

Before application this record described an additive migration: two nullable profile columns on shops (`email`, `governorate_code`), a public read-only 27-row governorate catalog, normalized-contact unique indexes, and a private registration reservation table. Existing rows can retain null new fields. No customer data is backfilled, wiped, or created. The authorization replacements remove confirmation prerequisites and revoke the legacy setup and invitation entry points. The initial development counts were zero users, shops, memberships, entitlements, and audit rows.

The reserved Auth id is generated on the server before Auth creation and deliberately has no Auth foreign key. Names, normalized contacts, governorate, UUID request key, status, shop id, and server UTC timestamps are stored; no password or hash is accepted by SQL. The same key and normalized profile return the same id. Uniqueness covers both reservation contacts, existing Auth contacts, and shop contacts. A different profile on the same key fails. The registration RPCs are service-role-only, with fixed empty search paths. API roles cannot read reservations or write the profile/catalog.

Codex corrected catalog naming to `egypt_governorates`, a nullable-phone constraint loophole, ambiguous PL/pgSQL column references, ASCII-only phone separators, and SQL test assertions for argument types and PostgreSQL's quoted empty search path. ### Server registration boundary

`owner-register` accepts POST JSON containing `idempotency_key`, `owner_name`, `business_name`, `email`, `phone`, `governorate_code`, and `password`. It validates all fields before reserving anything. Names are trimmed, 1..120 Unicode code points, without controls. Email is trimmed/lowercased and validated. Password is 8..72 UTF-8 bytes and is neither logged nor persisted outside Supabase Auth.

Phone supports local `01[0125]` plus eight digits, the same number as `+20`, and `0020`. Only ASCII spaces, hyphens and parentheses are removed. Stored shop/reservation form is `+201[0125]` plus eight digits; Auth receives the matching digits without `+`. Landlines, other prefixes, invalid lengths, non-Egyptian phones, and other punctuation are rejected. The server validates the 27 current ISO 3166-2:EG codes; Arabic display labels come from the read-only catalog.

The Edge calls `begin_owner_registration(p_request_key, p_owner_display_name, p_business_name, p_email, p_phone, p_governorate_code)`, then looks up the reserved id through Auth admin. Only an explicit not-found permits `createUser` with that id, both contacts, password, and `email_confirm: true` / `phone_confirm: true`. Those technical Auth flags suppress confirmation requirements; they are not ownership evidence. Unknown lookups fail closed. Lost create responses reload that same id. The Edge proves the submitted password through separate ephemeral public-key email/password and phone/password calls, requiring both to return the reserved id. It never resets the password on a retry or attaches an unrelated user.

`complete_owner_registration(p_request_key)` checks the reserved Auth identity and atomically creates one shop, one owner membership, one audit event, and the completion state. It returns the shop UUID. A completed replay returns that same shop. Time zone is `Africa/Cairo`; no entitlement or trial is inserted, so the shop is pending activation. A partial failure leaves no usable partial shop and can reconcile with the same key. Reservations are retained; there is no destructive cleanup job.

Success is HTTP 200 `{status:"completed",user_id,shop_id}`. Errors are `invalid_input` (400), `invalid_credentials` (401), `identifier_taken` / `request_key_reused` (409), `registration_identity_mismatch` (422), and `unavailable` (503). No token, password, hash, or contact is echoed. Requests require the configured public API key, reject secret keys, and cap body consumption at 16 KiB. Codex added a stream-cancellation regression. The service-role key remains in the server client only.

The user explicitly approved development-only deployment after automatic approval review required that authorization. `owner-register` is ACTIVE, version 1, deployment bundle SHA-256 `517666753558adb4ca68c18b4e79b50892156e2befd46dbe81ca2adb3fbd4b31`. Platform `verify_jwt` is false because registration precedes a user session; the handler enforces its own public API-key check. No staging or production function was deployed.

### Authorization and client contract

Confirmation timestamps and user metadata do not authorize access. Membership, revocation, grants, entitlements, and independent `platform_admins` checks remain authoritative. A presented JWT session id must match the actor's live `auth.sessions` row; malformed, missing-row, other-user and expired-session ids fail. Fixture-only impersonation with just `request.jwt.claim.sub` remains supported; hosted Auth tokens have a session id. D13 read access after entitlement expiry and write denial remain intact. Newly pending shops have no entitlement and cannot read shop tables.

Legacy `create_shop_account`, `create_staff_invitation`, and `accept_staff_invitation` execute permissions were revoked for API/service roles because they bypass the new required profile or bind to unverified contact ownership. Existing grant/revoke commands remain unchanged. No invitation or grant screen was built. React still signs platform administrators in with email/password and requires `is_platform_admin`; it no longer requires an email confirmation timestamp and offers no owner registration.

Flutter uses domain-owned authentication/registration interfaces, validated identifiers and profile objects, a Supabase adapter, and separate Arabic RTL presentation. Login switches between email and phone. Signup requires all six fields and loads governorate display labels from the server catalog. Duplicate submissions are disabled. One UUID request key and normalized payload are retained through retry. After confirmed Edge completion the adapter signs in and verifies the session user matches the server id; only then does the gate call `list_my_shop_accounts`. Theme persistence and palette tokens, selection, empty membership lists, pending, active, expired, session expiry, and membership-loss behavior remain covered. The obsolete post-login shop setup form and its adapter method were removed.
