# Invoice message v1

Owner-confirmed D35 / [ADR 0022](../../docs/adr/0022-invoice-message-templates.md). Applied to authorized development on 2026-10-19 with a separately reviewed actor-index follow-up: [mapping and preservation](../../docs/reviews/invoice-messaging-2026-10-18/deployment-2026-10-19.md). Native/two-device/owner acceptance remains open.

`get_invoice_message_v1()` returns `version=1`, `shop_id`, decimal-string `revision`, nullable normalized `template`, `can_write`, `time_zone`, nullable `created_at` (server UTC) and `created_at_shop`. Absent profile is revision `0`, null template/timestamps; reads never backfill defaults. Null means the existing four-line default in the [reviewed contract](../../docs/operations/invoice-messaging-slice-prompt-2026-10-18.md).

The exact command payload is `{version:1,kind:"invoice_message",expected_revision:"0",template:null|string}`. `review_invoice_message_v1(p_payload)` returns `ready|stale|expired`, `current_revision`, `can_write` and normalized fields when ready. `post_invoice_message_v1(p_idempotency_key,p_payload)` atomically locks the shop, checks owner/entitlement/revision, appends one revision and metadata-only audit, stores the exact original request/result, and bumps only message/global sync revisions. No open day is needed. The receipt identifies shop/key/kind/actor, original payload, new revision/template, server UTC `at`, `replayed`, zero cash/gold/stock strings and false invoice/dispatch effects. Same key and original payload returns the original result before the active-entitlement check; changed payload fails `payload_mismatch`. Stale expected revision fails `stale_message`.

`get_invoice_message_status_v1(p_idempotency_key,p_payload)` returns `absent` or `completed` with the original receipt. Authorized expired owners can read, reconcile and replay existing results. New writes require an active entitlement. Anonymous, revoked, other-shop and implicit platform-admin access are denied. Clients have select-only owner RLS, no direct writes; all three tables are append-only. Audits store revision/key/owner/server time and template length/hash metadata, never template text, rendered body or recipient phone. Separate request records retain the exact command for recovery.

`get_invoice_message_source_v1(p_operation_id)` reads operation facts and current message revision in one server snapshot: operation/shop IDs, kind, sequence, current registered name/zone, UTC and matching server-local operation time, immutable payload/content hash and nested message profile. It has no write effects. It does not include current payable remaining, CRM data or appearance settings. Existing financial and dispatch functions stay unchanged.

Grammar, allowlist and optional values are exactly the reviewed D35 contract. Normalize CRLF; reject any remaining CR before Unicode trim. Trim Dart whitespace, then validate at most 400 Unicode scalars/eight LF characters. Reject C0/C1/DEL and the shared explicit format/noncharacter set; allow ZWJ and variation selectors for emoji. Malformed UTF-8/surrogates fail at the database boundary; Dart checks UTF-16 explicitly. Escapes are `{{`/`}}`; tokens are single-pass and never recursively substituted. The client additionally checks rendered output (500 scalars) and the actual encoded URI (1800 ASCII characters), without truncation. Literal text is always plain text; there is no HTML/URL/expression evaluator or remote-content lookup.

Pending storage keeps the original key and envelope through timeout/crash/status/retry, and refuses to replace unrelated or unknown commands. Handoff binds owner/token epoch, shop, full operation facts/hash, template revision/text, renderer version, name, zone and snapshot destination; it rereads before launch. A change replaces the preview and requires another explicit action. Launch has opened/unavailable/failure/unknown outcomes and no cancellation/delivery claim. The adapter never posts a financial command or confirms dispatch.

The new `message_revision` sync scope is independent from appearance. Reconnect/resume performs authoritative reads. Settings preserve dirty drafts and reject stale overwrites. Template-save, operation and owner-confirmation times retain separate meanings. The legacy PDF and explicit branded-copy actions remain separate.
